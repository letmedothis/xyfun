# ELECT-001/002/003/009

## Original Issue

FS IPC handlers (FS_EXIST, FS_DELETE, FS_FILE_READ, FS_FILE_WRITE, FS_DIR_READ, FS_DIR_CREATE) accept arbitrary filesystem paths with no path sandboxing. The `isTrustedSender()` check only verifies the sender URL, not the path scope.

## Root Cause

The IPC handlers only checked `isTrustedSender()` but never validated that the requested path was within allowed directories. The `resolveWithinPath()` utility existed but was never used in IPC handlers.

## Fix

Added path sandboxing to all FS IPC handlers. Created an `isPathAllowed()` helper that validates paths are within allowed directories (APP_STORE_PATH, APP_FILE_PATH, APP_DATABASE_PATH, APP_PLUGIN_PATH, APP_TEMP_PATH, APP_LOG_PATH).

## Files Changed

- `src/main/ipc.ts`

## Behavior Before

1. Renderer calls `ipcRenderer.invoke('fs:file-read', '/etc/shadow')`
2. `isTrustedSender()` checks sender URL
3. `readFile('/etc/shadow')` executes without path validation
4. Returns file contents

## Behavior After

1. Renderer calls `ipcRenderer.invoke('fs:file-read', '/etc/shadow')`
2. `isTrustedSender()` checks sender URL
3. `isPathAllowed('/etc/shadow')` returns false
4. Returns null (rejected)

## Regression Risk

MEDIUM - If the renderer legitimately accesses paths outside the allowed directories, those operations will now fail. Need to verify all legitimate FS access patterns.

## Remaining Risk

The path validation uses `resolveWithinPath()` which resolves symlinks, but there may be TOCTOU edge cases. The allowed directory list may need expansion for legitimate use cases.
