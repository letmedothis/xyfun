本文汇总当前仓库中尚未直接修改、仍存在明确 TODO、平台缺口或已知限制的项目，作为后续迭代的设计基线。方案以现有 TypeScript、Vue、Electron、Rust/NAPI 和 libVLC 架构为约束，优先采用现有模块和第三方库能力。

## 2. 范围与优先级

优先级定义：

- P0：影响核心播放、跨平台可用性或存在明显安全/稳定性风险。
- P1：影响主要功能完整性或长期维护成本。
- P2：体验优化、类型收敛或工程治理。

实施顺序建议：P0 → P1 → P2；每项均应先补测试或可复现用例，再实现代码。

## 4. 详细设计

### 4.1 VLC Windows/Linux 视频窗口适配（P0）

#### 现状

`@zy/vlc` 原生层通过 NAPI 调用 libVLC。macOS 使用 `NSView` 作为视频输出容器；Windows 的 `HWND` 和 Linux 的 X11 `Window` 已拆分为独立平台模块，并按 Electron 返回的本机宽度、本机字节序解析句柄。各平台会拒绝长度错误、零值及超出 libVLC `uint32_t` 范围的 X11 句柄，并在缺少对应 libVLC setter 时返回明确错误。

当前开发环境缺少 Rust 工具链，尚未执行原生编译与 Windows/Linux 实机播放验收。Linux 仅支持 X11/XWayland，纯 Wayland 原生句柄不能传给 `libvlc_media_player_set_xwindow`。

#### 设计

1. 已新增 `platform/windows.rs`，使用 Windows 原生窗口句柄调用 `libvlc_media_player_set_hwnd`。
2. 已新增 `platform/linux.rs`，使用 X11 窗口句柄调用 `libvlc_media_player_set_xwindow`。
3. 已在 `platform/mod.rs` 中按目标平台条件编译导出模块，并集中处理原生句柄长度校验。
4. 保持 TypeScript 层 API 不变，平台差异只存在于 Rust 原生层。
5. 对句柄、矩形尺寸和 libVLC setter 缺失进行校验，统一转换为 NAPI 错误。
6. 窗口尺寸变化继续复用 `state.video_rect`，避免在 renderer 侧维护第二套布局状态。
7. Linux 首期明确 X11 支持范围；Wayland 不直接承诺，若无法取得 XWindow，应返回可诊断错误并保留浏览器播放器回退。

#### 依赖与风险

- 需要确认 Electron 当前运行环境和 libVLC 版本对 X11、Win32 输出接口的支持。
- Windows/Linux CI 需要能加载对应动态库，至少增加编译检查和句柄绑定的集成验证。
- Rust FFI 调用必须与平台线程模型及窗口销毁时机匹配，避免悬空句柄和崩溃。

#### 验收标准

- Windows、Linux、macOS 均能完成创建、播放、暂停、销毁和窗口尺寸变化。
- 父窗口销毁或播放器销毁后不再访问原生句柄。
- 缺少 libVLC setter、无效句柄和不支持的显示协议均能返回明确错误。
- 原有 macOS 行为和 TypeScript API 不回归。

### 4.2 t3Drpy 验证码与首页分类筛选（P1）

#### 现状

t3Drpy 内置脚本中标记“验证码识别”和“首页分类解析/筛选”尚未实现。适配器还包含 worker、注入脚本、模板和多种加密库，不能通过简单的前端补丁解决。

#### 设计

1. 先定义统一的验证码结果模型：验证码类型、图片/挑战地址、会话信息、过期时间和失败原因。
2. 在 drpy worker 与主进程适配器之间增加可取消的验证码请求通道；验证码不得阻塞整个 worker 池。
3. 首期只接入已有脚本能够提供的验证码交互，不内置绕过或自动破解逻辑；需要用户操作时由上层展示交互提示。
4. 首页筛选先解析脚本返回的分类、筛选项和选中值，归一化为现有影视 API 的筛选结构；无法识别的字段保留原始信息并记录诊断日志。
5. 将解析失败、超时、用户取消和源不支持区分处理，避免统一显示为空数据。
6. 为脚本执行增加输入边界、超时、资源限制和日志上下文，避免异常脚本影响其他源。

#### 验收标准

- 验证码源可显示挑战、提交结果、取消和超时，并能恢复后续请求。
- 不支持验证码或筛选的源仍可正常打开，不影响其他源。
- 首页分类筛选在至少一种标准 drpy 源上能完成分类加载、选项加载和结果刷新。
- worker 异常不会导致主进程请求永久挂起；关键失败原因可在中央日志中定位。

### 4.3 弹幕发送插件生命周期完善（P1）

#### 现状

`DanmuSendPlugin` 已加入非音频播放器插件列表，并在 `onPluginsReady` 后获取 danmu 实例。点击与 Enter 发送使用稳定的实例回调，销毁时解除事件并清空引用；发送前会校验空白、最大长度、播放时间和 danmu 可用性，失败时保留输入并发出 `DANMAKU_SEND_ERROR`。

#### 设计

1. 已在 `onPluginsReady` 获取 danmu 插件；无可用 danmu 渲染实例时禁用发送控件。
2. 已在 `afterCreate` 集中绑定按钮和输入框事件，支持 Enter 发送。
3. `sendBtnClick` 已统一校验空白文本、最大长度、当前播放时间和 danmu 插件可用性；发送失败时保留输入内容并发出失败事件。
4. `destroy` 已解除事件、清空引用和状态，避免播放器重建后重复触发。
5. 发送事件保留原始弹幕数据；传给渲染插件的弹幕使用延迟后的毫秒时间。

#### 验收标准

- 播放器创建、切换媒体、销毁、重建后均只存在一组事件监听。
- 无 danmu 插件、空文本、超长文本和发送异常均有稳定行为。
- 鼠标和 Enter 操作结果一致，国际化文案保持可用。
- 发送成功后清空输入，失败时不丢失用户输入。

### 4.4 播放器已知兼容性问题治理（P1）

#### 已知问题

播放器 README 记录了 DASH 请求头无法完整传递、xgplayer 切换 MPD 失败、oplayer 音量/倍速记忆偶发失效、nplayer 不支持多画质，以及不同播放器的静音显示、右键、国际化和弹幕能力不一致等问题。

#### 设计

1. 建立统一播放器能力矩阵，由适配器声明 `type`、请求头、画质、弹幕、切换、记忆和右键能力。
2. 播放页根据能力矩阵决定是否展示控件，不让用户点击必然失败的功能。
3. 对 DASH 请求头采用能力降级：首个 MPD 请求可带头时继续传递；分片请求无法传递时记录告警并提示源限制。
4. 将播放器切换拆分为“同实例切换”和“销毁重建”，由适配器明确选择，统一清理监听与插件状态。
5. 用跨播放器行为测试覆盖播放、暂停、seek、音量、静音、倍速、画质、弹幕和下集切换。

#### 验收标准

- 能力不支持时 UI 不展示或明确标识，不出现无反馈点击。
- 播放器切换不产生重复事件、错误的进度记录或错误的下集跳转。
- 关键兼容性差异在测试矩阵中有明确结果，而不是依赖 README 手工记忆。

### 4.5 worker 日志转发（P1）

#### 现状

渲染器日志工具中存在“支持 worker 将日志发送到主进程”的 TODO。worker 环境无法直接使用主进程 logger，可能导致关键解析或播放问题缺少统一日志。

#### 设计

1. 定义最小日志消息结构：级别、模块、消息、上下文、时间戳和可选错误信息。
2. worker 端优先使用 `postMessage`，由创建 worker 的 renderer 模块集中接收并转交现有日志桥接。
3. 主进程接收后使用 `loggerService.withContext` 写入中央日志，禁止把任意 Node API 暴露给 renderer。
4. 增加消息大小限制、敏感字段过滤和异常序列化处理。
5. worker 结束时移除监听；日志桥接不可用时保留受控的 renderer fallback。

#### 验收标准

- worker 日志能在主进程日志中按模块检索。
- worker 崩溃、消息格式错误和桥接不可用不会导致业务失败。
- 不记录令牌、Cookie、完整播放地址中的敏感参数等隐私信息。

### 4.6 Electron 构建 warning 治理（P2）

#### 设计

1. 逐条确认 `electron.vite.config.ts` 被忽略的 warning 来源和影响范围。
2. 优先通过依赖升级、类型声明、构建入口调整或 externals 配置解决。
3. 对确实无法消除的第三方 warning 增加精确匹配和注释，禁止扩大忽略范围。
4. 将构建日志检查纳入 CI，避免新 warning 被静默吞掉。

#### 验收标准

- 已知 warning 数量下降或每条都有明确原因。
- `typecheck`、`lint`、`test` 和生产构建均通过。
- 不因压制 warning 导致运行时模块缺失。

### 4.7 TDesign 菜单类型收敛（P2）

#### 现状

`MenuRoute.path` 当前使用 `any`，原因是 TDesign 菜单组件支持字符串但类型声明不匹配。

#### 设计

1. 先确认当前 TDesign 版本的官方类型和组件实际入参。
2. 若上游类型已修复，升级或调整本地类型引用，并删除 `any`。
3. 若上游仍未修复，在本地定义最小的兼容类型边界，只对菜单组件适配处做类型转换，不扩散 `any`。
4. 增加路由菜单构建的类型测试，覆盖字符串路径、动态路由和子菜单。

#### 验收标准

- `MenuRoute.path` 具有明确的字符串/路由类型。
- 菜单渲染、跳转、刷新和动态路由行为不变。
- 不再依赖无法解释的全局 `any`。

## 6. 通用实施与验证要求

每个项目完成前应满足：

1. 先补充可复现用例和边界条件，再实现功能。
2. 主进程路径使用 `application.getPath`，日志使用 `loggerService`；renderer 仅在既有约定范围内记录日志。
3. IPC 输入在主进程校验，worker 消息进行大小、字段和敏感数据校验。
4. 变更目录前阅读该目录及父目录 README/AGENTS 约定，并检查相关依赖补丁。
5. 完成后运行 `pnpm lint`、`pnpm test` 和 `pnpm format`；涉及原生包时额外运行对应构建和类型检查。
6. 按单一主题提交 Conventional Commit，并使用 `git commit --signoff`。
