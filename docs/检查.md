# Bug 分类

最终原则：

宁可只报告 15 个真实高质量问题，

也不要输出 200 个静态分析警告。

你的任务不是证明代码“不完美”，

而是找到：

“用户真正使用这个应用时，哪里会坏、哪里会慢、哪里会崩、哪里会越来越卡。”

现在开始。

第一步先扫描整个项目结构，并输出项目架构理解。

在完成架构理解之前，不要开始输出 Bug。

建议你在 Codex 第一轮跑完后，**不要直接改代码**。最好再单独开第二轮，让 Codex 对第一轮找到的 Bug 做一次“复核 + 反证”，尤其 Electron + Rust 很容易因为没有完整追踪生命周期而误报。

如果你想把效果再提高一档，第二轮可以直接用这一句：

> 对上一轮所有 Critical、High 和 Medium 问题逐个重新验证。你的任务不是继续找 Bug，而是尽可能证明每个 Bug 不成立。必须重新读取调用方、被调用方、类型定义、IPC 参数、Rust Result/Option 处理、生命周期和异常路径。只有无法被反证的问题才能保留。对于保留的问题，给出可以稳定复现它的最小步骤或测试代码。

这样会比只让 Codex 扫一次可靠很多。
