# 数据库升级与恢复

当前 SQLite 升级路径支持数据库版本 3.4.1 至 3.4.8，应用 3.4.9 会将数据库升级到 3.4.9。3.4.9 修正旧版历史索引，只有影视、直播、解析播放记录参与去重；搜索和导入历史不再因来源相同而被合并。

已经被旧版迁移删除的搜索词不会自动恢复，需要升级前的备份。旧 zyplayer 目录、Dexie/IndexedDB、PGlite 的自动转换尚未实现，不能将这些数据文件直接当作 SQLite 使用。

## 升级前备份

已有且结构匹配的 SQLite 数据库在迁移前自动生成一致性快照，包含已提交但尚未 checkpoint 的 WAL 数据。位置为：

```text
<userData>/database/backups/before-<旧数据库版本>-to-<新数据库版本>-<随机后缀>/data.db
```

备份不会覆盖以前的快照，也不会自动清理。日志中的 `Database backup created` 表示备份已完成完整性检查和文件同步；没有该成功日志的文件可能是失败操作留下的不完整备份。备份失败会阻止迁移，不能通过删除原数据库绕过错误。

备份只覆盖 SQLite 数据库，不包含插件文件、localStorage、浏览器登录状态、用户脚本或外部工具。完整升级回归仍应在程序完全退出后备份整个用户目录及自定义目录。

数据库版本缺失、损坏、超出支持范围，或表字段／历史索引与版本不匹配时，程序会停止初始化并记录原因，不会清空后重建。3.4.1 以前的 SQLite 结构需要单独转换。

## 恢复注意事项

1. 完全退出应用，保存当前 `database` 目录的副本；不要在进程运行时替换数据库。
2. 对准备恢复的快照运行 `sqlite3 <快照路径> "PRAGMA integrity_check;"`，结果应为 `ok`。
3. 将当前 `data.db` 及其存在的 `data.db-wal`、`data.db-shm`、`data.db-journal` 一起移到独立保留目录，再将快照复制为 `database/data.db`。不要让旧旁路文件与恢复的数据库混用。
4. 使用支持该数据库版本且包含搜索历史修复的程序启动，核对历史、收藏、设置和源配置。新版本会重新备份并迁移旧快照。

不要将已经升级后的数据库直接交给更老应用；恢复到旧程序时应使用对应旧版本的完整备份。备份含云端凭据等用户配置，应按原数据库的敏感程度保管。

## 自动化回归

```bash
pnpm exec vitest run --project upgrade
```

该测试项目使用真实临时 SQLite 文件和文件系统，不继承普通主进程测试的文件系统 mock。`src/main/services/DbService/__tests__/fixtures/3.4.1.sql` 固定来自历史提交 `3e6a62a3`，不得用最新建表脚本替代。

测试覆盖跨版本升级、已执行旧 3.4.8 的修复、搜索和导入历史保留、播放进度与主键、收藏和配置、备份失败、WAL 快照、迁移异常回滚、重启幂等，以及错误版本／Schema 的拒绝处理。

三平台安装器、自动更新、真实强杀／断电和旧引擎转换仍需独立回归；这些数据库测试不能替代安装级验证。
